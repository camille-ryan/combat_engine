# A UI for the story engine

Camille, 2026-10-29: *"Build a UI for the story engine. Let godmode be an
option in settings in the UI."*

## The one hard problem

`beat.play_scene` is a **blocking loop that calls back for human input**:

```
while not playing.over:
    made = one_beat(playing, table, actors, director,
                    ask_human=ask_human, party_level=party_level)
    after(made)
```

`ask_human(actor, situation) -> (speech, doing)` blocks until the person
answers, and `after(beat)` fires as each beat lands. An HTTP handler
cannot block for thirty seconds waiting for a POST, and a scene with the
14B DM takes 18.7s **per beat** before anybody types anything.

Two ways out:

1. **Run the scene on a worker thread.** `ask_human` blocks on a
   `queue.Queue` that `POST /say` fills; `after` pushes each finished beat
   onto an SSE stream. `beat.py` and `run.py` are untouched.
2. **Turn the loop into a state machine** that returns after each beat and
   is re-entered by the next request. A real change to `beat.py`, and it
   would have to carry `Playing` across requests anyway.

**Take (1).** `api/session.py` already holds one encounter across
requests, so server-side session state is the established shape here, and
SSE is already how the fight page gets its events (`EventSource` in
`app.js:1308`). (2) rewrites the most carefully-measured file in the
component to gain nothing a thread does not.

## Endpoints, following `app.py`'s existing shape

```
POST /api/story                 -> StoryStateDTO   start: module, seed, god
GET  /api/story/{id}            -> StoryStateDTO   where the campaign is
POST /api/story/{id}/advance    -> StoryStateDTO   play the next scene
POST /api/story/{id}/say        -> StoryStateDTO   the player's line for this beat
GET  /api/story/{id}/events     -> SSE             lines as they land
```

`advance` returns immediately; the scene plays on the worker and the page
watches `events`.

## What crosses the wire

**#930 is a prerequisite, not a nicety.** `Step.lines` is a flat
`list[str]`, so the page would have to pattern-match prose to know a roll
from the DM's paragraph. Camille asked for rolls and knowledge to be
styled differently, which cannot be done on a flat list.

So a line becomes `{kind, text}` with a closed vocabulary:

| kind | who wrote it |
|---|---|
| `scene` | the adventure |
| `recall` | the engine's dice (`You know:` / `X knows:`) |
| `roll` | the engine's dice (a ruling) |
| `mine` | the person |
| `dm` | the model |
| `note` | the engine, out-of-story (a clamp, the god-mode banner) |
| `exit` | the adventure, closing the scene |

That split is the same one the graph already draws between `page`,
`earned` and `invented`: **who wrote a line governs how much it should be
trusted**, and the CSS should say so.

## Names

`wire.py` is the only component allowed to turn refs into names, and
`CE_NAMES=off` must serve refs. **The story UI mostly does not go through
it**: a scene's prose and its word for a creature come from the user's own
module file, which is git-ignored, and `play.py` already states that
nothing in that path reads `localization/names.json`. Anything that *is*
a ref -- a monster with no module word -- still goes through `wire`.

## God mode in settings

`web/CLAUDE.md`: the settings panel already keeps `dnd4e.freeform` and
`dnd4e.speed` in `localStorage`. God mode joins them as `dnd4e.godmode`,
passed on `POST /api/story`.

It must keep saying so. `story/CLAUDE.md`: *"`--god-mode` hands over every
fight and says so, every time"* -- the banner, the scene line and
`Step.notes` all carry it, and the page has to render that `note`
prominently rather than swallowing it. A god-mode run that looks like a
played one is the failure to avoid.

## Order

1. `#930` line kinds, with the CLI printing exactly what it prints now.
2. `api/story.py` + the worker, with `--no-llm` so it is testable offline.
3. `web/story.html`, `story.js`, CSS for the seven kinds.
4. Settings: god mode.
5. `scripts/browser.py` coverage -- it is "the entire cover" for `web/`.
6. Then `#931`, streaming and the thinking indicator, which needs
   `stream: true` and a `(phase, chunk)` channel.
