## The one piece of leverage: a differential threat term

**#266, #271, #283 and #305 all want the same capability**, and Camille's answers
to three of them say so independently:

* #266 — "a differential threat removal calculation"
* #305 — "determine the current total enemy threat and only use limited resources
  when threat is above some threshold"
* #283 — "a lookahead to next round's damage, and that part could be extensible to
  other classes"

That is one term in `policy/`, not four fixes. It is also the thing #293 is about,
so building it answers #293's open question by measurement instead of by picking a
multiple.

**Camille's acceptance test for it is explicit and is the guard to build against:**

> with 4 party members remaining and 1 enemy remaining, a single target power is
> still preferred over blasting the party

Plus the one already on #293: **the wizard must keep charging zero times.**

**Two warnings carried in**, both paid for today:

* `reach_gained` is `best_from(dest) − best_from(here)`. Any penalty netted into
  `best_from` lowers *both* ends, so it reads as "anywhere but here" rather than
  "there". A term built as a difference of baselines cannot express "avoid this
  consequence". That is why the friendly-fire attempt made friendly fire worse
  (party blasts clipping an ally 20 → 25) and was reverted.
* Judge it with the friendly-fire counter now in `scorecard.py`, not with
  `explain()`. `explain` filters to `DOCTRINE` and `allies_caught` is in
  `policy.features`' table, so it read 0 in every state including with the −7.0
  deterrent disarmed. The live baseline to beat:

```
                               party        monsters
level  5   blasts               20              4
level 10   blasts               19             93
           allies hit, bodies   26            166
```

```markdown
---
name: work-issue
description: Implement one GitHub issue end to end
background: false
arguments: [issue]
---
Work GitHub issue #$issue.

!`gh issue view $issue --json body,comments --jq '.body, (.comments[] | "=== COMMENT ===", .body)'`

**Read every comment above before starting.** In this repo the body goes stale and
the comments are the current state — #217's last comment reverses its own verdict.
If nothing printed, run it again as `gh issue view $issue --comments`.

1. Read the `CLAUDE.md` for the component you are working in, and `docs/AUTHORING.md`
   before writing any content row.
2. Implement it. Commit to master with `git cc` (author `Claude (Camille)`), one
   `Closes #N` per issue. No branch, no PR — that is not how this repo records work.
   If `git cc` is missing it is an untracked alias; use
   `git -c author.name='Claude (Camille)' -c author.email='rdbrady@gmail.com' commit`.
3. **Never write a test.** There are none and none should be written. Verify with
   `uv run scripts/check.py --fast`, or narrowly: `uv run scripts/audit.py <refs>`,
   `uv run scripts/lint.py`, `uv run scripts/show.py <ref>`.
4. **Never put a printed name in a tracked file** — not a comment, docstring,
   variable, commit message or issue. Refs only. Search the web for a *mechanic* you
   do not understand, never for a name.
5. A row is fully implemented before it is added, or it carries one marker naming
   one gap: `todo=` refused in play, `dropped=` plays with one clause missing,
   `narrative=("skill:x",)`, `obsolete=`.
6. If a design question blocks you, label the issue `needs-decision`, comment the
   question with the cost of each answer measured rather than guessed, and stop.
7. Re-read the comments before committing, in case Camille has answered.
8. Close with the measurement: what landed, what moved, how it was verified, and
   what you did **not** do. "Done" is worth nothing to the next reader.
```
